## Overview

Release `v2.6.0.70` delivers a comprehensive, enterprise-grade **Health Data Interoperability & Privacy Engine** for CoreHealth v2. It provides native, simultaneous compatibility across **HL7 FHIR R4**, **openEHR ITS-REST**, **OpenEMR REST**, and **HL7 C-CDA XML**, fully aligned with the statutory mandates of the **Nigeria Data Protection Act (NDPA 2023)**.

Designed around the **Zero Core Schema Mutation Invariant** and the **Controller Proxy Architecture**, all external inbound mutations (`POST`, `PUT`, `PATCH`) are mapped into standard Laravel requests that invoke existing production hospital controllers. This guarantees that all 46+ Eloquent observers execute, double-entry General Ledger journal entries balance (DR Cash / CR Revenue), and FIFO pharmacy inventory decrements occur without duplicate business logic or code drift.

## Key Enhancements

### 1. Five-Level Multi-Standard Interoperability Architecture
- **Level 1 — HL7 FHIR R4 REST API**:
  - Implements Level 1–4 FHIR capabilities across 8 core clinical and administrative resources: `Patient`, `Practitioner`, `Observation` (Vitals Panel), `Encounter`, `MedicationRequest`, `ServiceRequest` (Laboratory Orders), `DiagnosticReport`, and `Invoice`.
  - Publishes public `GET /api/fhir/r4/metadata` returning a compliant `CapabilityStatement` (FHIR v4.0.1).
  - Supports multi-token identifier querying (`system|value`), pagination via `_count`, and FHIR `OperationOutcome` error formatting.
- **Level 2 — openEHR ITS-REST Archetyped Storage & AQL Engine**:
  - Complete EHR lifecycle management: `POST /api/openehr/v1/ehr`, `GET /api/openehr/v1/ehr/{ehr_id}`, and search by subject ID (`GET /api/openehr/v1/ehr?subject_id={id}`).
  - Encapsulates consultation encounters and vital sign observations in standard openEHR COMPOSITION format (`openEHR-EHR-COMPOSITION.encounter.v1`, `openEHR-EHR-OBSERVATION.blood_pressure.v2`, `body_temperature.v2`).
  - Native Archetype Query Language (AQL) engine at `POST /api/openehr/v1/query/aql` returning standard openEHR `RESULT_SET` structures with columns and rows.
- **Level 3 — OpenEMR Compatibility & HL7 C-CDA Continuity of Care**:
  - Table-parity REST endpoints replicating OpenEMR table schemas: `/apis/default/api/patient` (`patient_data`), `/apis/default/api/encounter` (`form_encounter`), and `/apis/default/api/vital_signs`.
  - Export of HL7 Continuity of Care Documents (C-CDA R2.1 XML) via `/apis/default/api/ccda/{patientId}` featuring valid `ClinicalDocument` root, HL7 OID template identifiers (`2.16.840.1.113883.10.20.22.1.2`), patient demographics, encounters, vitals, medications, and allergies.
- **Level 4 — Standard Terminologies & Bidirectional Translation**:
  - Standardized LOINC & UCUM bindings for vital signs and laboratory parameters, WHO ATC for medications, and ICD-10 for diagnostic coding.
  - Powered by isolated auxiliary mapping table `interop_terminology_maps` seeded with 35+ standard clinical parameters.
- **Level 5 — Controller Proxy Architecture (Local Work Parity)**:
  - Inbound mutations mutate external payloads to proxy production controllers (`PatientController@store`, `VitalSignController@store`, `EncounterController@addSinglePrescriptionRequest`, `EncounterController@addSingleLabRequest`, `BillingWorkbenchController@processPayment`).
  - Preserves all double-entry general ledger postings and FIFO batch stock deductions.

### 2. Statutory NDPA 2023 / NDPR Privacy Compliance
- **Dynamic Sensitive Data Consent Ledger (`CheckNdpaConsent` Middleware)**:
  - Enforces affirmative patient consent under Section 30 for sensitive clinical processing.
  - Returns `403 Forbidden` (`NDPA_CONSENT_REQUIRED`) when secondary processing (`RESEARCH`, `CLOUD_AI`, `THIRD_PARTY_TRANSFER`) lacks active consent.
  - Preserves emergency direct clinical care under `DEFAULT_VITAL_INTEREST` per NDPA Section 30(2)(a).
  - Injects statutory compliance headers (`X-NDPA-Consent-Status: CONSENT_VERIFIED` or `DEFAULT_VITAL_INTEREST`) on all responses.
- **Pediatric Minor Guardian Verification (Section 31)**:
  - Dedicated auxiliary schema migration (`patient_consents`) storing `parent_guardian_name`, `parent_guardian_nin`, `parent_guardian_relationship`, and automatic `is_minor` calculation (< 18 years).
- **Consent Revocation (Section 34)**:
  - Instant revocation endpoint `DELETE /api/ndpa/v1/consent/{id}` transitioning consent status from `ACTIVE` to `REVOKED`.
- **Cross-Border Audit & AI Pseudonymization (Sections 41–43)**:
  - Deterministic pseudonym generator producing persistent UUID tokens for cross-border cloud AI services (e.g., Gemini AI).
  - Structured daily audit logging for cross-border transfers specifying target service, pseudonym, data category, and statutory safeguards.
- **High-Precision Free-Text PII Sanitizer (`NdprSanitizerService`)**:
  - Redacts patient names, Nigerian phone numbers, emails, 11-digit NIN, 11-digit BVN (`[REDACTED_BVN]`), 10-digit NUBAN bank accounts (`[REDACTED_ACCOUNT]`), chart numbers, honorific personal names (`[REDACTED_NAME]`), and kinship / next-of-kin references.

### 3. OWASP API Top 10 Security & Access Control
- **`AuthenticateInterop` Guard Middleware**:
  - Enforces authentication across all interoperability routes using Sanctum Bearer Personal Access Tokens (PAT), Web sessions, or SHA-256 Basic Auth.
  - Public exemption strictly scoped to `GET /api/fhir/r4/metadata`.
  - Rejection with `401 Unauthorized`, `WWW-Authenticate: Bearer realm="CoreHealth Interoperability API"`, and FHIR `OperationOutcome`.
- **Broken Object Level Authorization (BOLA/IDOR) Isolation**:
  - Patient-level tokens are strictly confined to their own compartment (`FhirPatientController@show`, `PatientConsentController@show`). Attempts to query another patient's chart abort immediately with `403 Forbidden`.
